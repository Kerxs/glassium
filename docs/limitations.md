# 限制与编写规则

> 这一页描述的是**架构定义**，不是待办事项。先读这三条规则，否则第一次用就会遇到
> 「玻璃完全不可见」。T9 起违反 R1 时控制台会点名是哪个元素，但读过规则就不必等警告了。

## 三条编写规则

### R1 —— 面板与画布之间的每一层都必须背景透明

页面背景属于**场景**，不属于 CSS。要放背景图，用 `stage.setScene()`（见下文「用户场景」）。

Glassium 的画布**本身就是玻璃**：面板像素来自画布，而画布在所有 DOM 内容之下
（`z-index: -1`，理由见下文「画布为什么在 z-index: -1」）。面板和画布之间只要有一层画了背景，
那块画布就被挡住了。

失效表现是最难查的那一种：面板成为不透明盒子里的一个透明洞 —— **完全不可见**。
所以 Glassium 会查这件事，查出来就在控制台**点名具体元素**（`src/renderer/layering.ts`）：

```
[Glassium] glass-card#card.panel-card 的祖先 main.content 有不透明背景（rgb(255, 255, 255)），
把后面的玻璃整块挡住了 —— 玻璃完全看不见。R1：面板与画布之间的每一层都必须背景透明 ——
页面背景属于场景，不属于 CSS。
```

判据是浏览器自己的命中测试顺序（`document.elementsFromPoint`），不是沿祖先链推断。
所以它查得出**不是祖先的重叠元素**（整页的背景 div、另一张卡片），也不会把画在画布下面的
背景误报出来。什么时候查：注册时、面板进入视口时、页面上任何元素的 `style` / `class`
变化之后（节流 250ms），以及手动调 `stage.debug.checkLayers()`。

同一次检查还会报：

| 情形 | 为什么是问题 |
|---|---|
| 面板自身有背景 | 它自己就挡在玻璃前面 |
| 面板或祖先有 `filter` | 只作用在 DOM 上。常见的是 `drop-shadow`：玻璃不会有影子 |
| 面板或祖先有倾斜、透视、3D 旋转 | 玻璃只跟得上平移、缩放与（平面内的）旋转，形状对不上（见表下） |
| 画布画在面板上面 | 面板或祖先有负的 `z-index`，面板连同文字都被画布盖住 |

**旋转**（`transform: rotate`、`rotate` 属性，自己或祖先）：玻璃按转过的圆角矩形画 —— 包围盒的中心是它的中心，
尺寸是布局尺寸乘缩放，形状在面板自己的坐标系里算，折射方向、法线转回屏幕坐标；光源方向、投影方向仍是屏幕上的
（左上的光、往下的影子，不跟着转）。实测转 37° 的圆与不转的圆逐像素比，12.96 万个像素里 12 个差 1/255。
倾斜、带旋转的镜像、各层合起来成了平行四边形（转过的元素外面套一层不等比缩放）画不了，照旧按包围盒画并警告。
（第一期里这一行是「旋转、倾斜、透视都画不了」。）

**缩放**（`transform: scale`，自己或祖先）：玻璃跟着缩放后的盒子走，以 dp 计的量（圆角、模糊 σ、亮边、投影）也乘上
视觉缩放 —— 缩放动画（对话框从 0.9 放大到 1 之类）里玻璃与 DOM 一致。实测 `scale(0.5)` 里 200×100、圆角 24、
模糊 8 的卡片，与直接画的 100×50、圆角 12、模糊 4 的卡片逐位相同。
（这一行早先就写着「缩放没问题」，那时只有盒子跟着缩，圆角与模糊不缩。）

`opacity` 不报：玻璃跟着元素的**实际不透明度**（自己与祖先 opacity 的乘积，画布也在其中的共同祖先不算）
一起淡，CSS 的渐隐渐显（过渡、动画）直接可用 —— 每帧读计算样式，乘进材质的 opacity。
（第一期里这一行写的是「DOM 内容跟着变淡，玻璃不会，要让玻璃一起淡用材质的 opacity」—— 那时确实不跟。）

`opacity: 0` 与 `visibility: hidden` 不报 —— 这两种情况下面板直接不画（`checkVisibility()`），
渐隐收起的菜单不会在原地留下一块玻璃。

**关于 `<html>` 与 `<body>` 的背景：** 只给其中一个设背景没关系。`<html>` 没有背景时，
`<body>` 的背景会传播成根背景，画在一切之下（CSS Backgrounds 3 §2.11.2）。
**两个都设**时 body 的背景就画在画布之上了，检查会点名 `body`。

查不到的：只挡住面板一角的元素（只在面板内五个点上查）、`pointer-events: none` 的遮挡层、
不在视口里的面板（等它滚进来才查）。

（T1 到 T8 期间这一段写的是「Glassium 内置了祖先检查」，那时它并不存在。T9 才实现。）

### R2 —— 面板只折射 Glassium 场景：不折射 DOM，也不折射别的面板

玻璃背后的正文文字、图片、iframe **不参与折射**。这不是没做完，理由见下一节。

玻璃也不折射另一块玻璃。模糊链每帧只从场景建一次，所有面板都从它采样、再各自画上去 ——
两块玻璃叠在一起时，上面那块看到的是场景，不是下面那块，于是在下面那块的 tint 上开出一个洞。
所以别把 `<glass-button>` 放进 `<glass-card>` 里：并排放，或者让它们连成一组（`<glass-container>`）。
Apple 自己的规范也是「玻璃不叠玻璃」（SwiftUI 的文档原话是玻璃不能采样别的玻璃，所以要用 `GlassEffectContainer`）。

玻璃底下要有颜色 —— 开关的轨道、滑块的进度条、卡片后面的色块 —— 用 `<glass-fill>`：它的颜色不画在 DOM 里，
由 Glassium 画进场景，所以玻璃看得见它（见下文「填充」）。

（第一期的前 12 项里这一条的标题写的是「面板折射场景与 z-order 在其下的面板」—— 那是规划时的设想，
渲染器从来没有这么做过。）

### R3 —— 每文档一个 stage

浏览器的 GPU 上下文上限约 16 个，多 stage 会很快耗尽；而且多块画布之间无法互相采样，
`<glass-container>` 的合并也就失效了。第二次调用 `createGlassStage()` 会警告并返回同一个 ——
包括第一次还在等 GPU 设备、两次调用交错的时候。

组件**可以早于 stage** upgrade。`createGlassStage()` 要等 GPU 设备，是异步的，而
`customElements.define` 一执行，页面上已有的元素就立即 upgrade —— 「先建 stage 再 upgrade」
在实际页面里做不到。组件没有 stage 时先显示 CSS 兜底表面，stage 建好时统一注册；
stage 被 dispose 再重建，组件也跟过去。

（这条早先写的是「须在首个面板 upgrade 前创建」，T9 之前组件还不存在，这个约束也就没人验证过。）

### 画布为什么在 z-index: -1

T5 到 T9 期间画布在 `z-index: 0`，内容要放进 `position: relative; z-index: 1` 的容器里。
理由写的是「-1 会画到根背景之下」。**那是错的**：负 z-index 的层叠上下文画在根背景**之上**、
所有常规流内容之下（CSS 2.1 附录 E 的第 2 步）。实测 -1 时一点上的命中栈是
`[面板, main.content, body, 画布, html]`，画布在 html 之上，场景照常可见。

而 0 有一个实打实的代价：画布画在所有**不定位**的内容之上。没把内容包进 z-index ≥ 1 容器的
普通页面，正文会整个被画布盖住 —— 实测一行不定位的文字在 0 下消失、在 -1 下正常显示。
这恰好是第一次用的人最可能写出的页面。

-1 的代价只有上面那一条：`<html>` 和 `<body>` 都设了背景时 body 会挡住玻璃，检查会报出来。
这个结论是写 T9 的层级检查、拿命中栈对照两种设置时才发现的；与撤回采样余量那次一样，
规划阶段的推断没有被实际渲染验证过。

## 为什么玻璃折射不了任意 DOM

Web 平台今天不允许。四条独立理由，任何一条单独成立即可：

**1. 唯一能对实时 DOM 背景做几何位移的途径只有一家实现。**
`backdrop-filter` 的十个内置滤镜函数没有一个能做几何位移，折射只能经 `url()` + `feDisplacementMap`。
而 SVG 引用滤镜用在 `backdrop-filter` 上：Chromium 可以；WebKit 在
`RenderLayerBacking::updateBackdropFilters()` 里对 `hasReferenceFilter()` 短路且**没有软件兜底**，
bug 245510 自 2022-09-21 开着、实现 PR 至今未合；Firefox 从未实现，只在 106 里做了「优雅降级」
（渲染未滤镜的帧）。

更糟的是**探测不出来**：Safari 会把 `backdrop-filter: url(#x)` 解析成功但静默不渲染，
所以 `@supports` 返回 true。MDN 的 browser-compat-data 也没有这个子特性的条目
（请求它的 issue 被 closed as not planned）。

**2. 就算只面向 Chromium，SVG 路线也有硬天花板。**
位移贴图是 8bit 通道，所以位移被量化且锁死在 ±128px/轴，有可见色阶；没有超采样；
warp 场是静态的 —— 跟手的透镜、涟漪、缓动进出的扭曲**无法表达**，几乎每次尺寸或形状变化
都要重建整张位移贴图。

**3. 唯一能把实时 DOM 送进 GPU 纹理的途径还没落地。**
HTML-in-Canvas（`drawElementImageToTexture`）是 Chromium 的 origin trial，Gecko 与 WebKit
都是 "no signal"。而且出于隐私，它**排除 SVG、`url()` 背景图、跨源内容与次像素抗锯齿** ——
你折射到的背景和用户看到的背景不是同一个。图标消失、hero 图消失。这是正确性问题，
不是精细度问题。

**4. 通用兜底全是 DOM 重栅格化。**
html2canvas 自述「不是截图，而是按 DOM 属性重建一份表示」「永远不会完整支持 CSS」。
真实库的实测数字：单次快照中位数约 55ms，即约 18fps —— 那是快照，不是实时；
CSS 动画不参与折射；`position: fixed` 被忽略。

### 换来了什么

自持渲染面拿到的是 SVG 路线结构上拿不到的东西：

- **浮点精度位移**，没有 ±128px 上限，没有色阶
- **真正的逐通道色散**（不是单次采样近似）
- **任意动画扭曲场** —— 跟手透镜、涟漪，无需重建任何贴图
- **一次 pass 内合并多块玻璃**（`smin`）—— 这正是 Apple `GlassEffectContainer` 做的事，
  也是上游 issue #104 开着的缺口
- 任意形状，不限于预计算过的那几种

## 其它已知限制

### 画布恒为不透明，所以玻璃输出不钳 `rgb ≤ a`

（这一节早先写的是「Glassium 钳制 `min(rgb, a)`，代价是低 opacity 时高光被压平」，
并提到一个 `premultiplyViolations` 计数。钳制已在 T8 去掉，计数从未实现 —— 下面是现在的做法。）

预乘的不变式 `rgb ≤ a` 只在**画布与页面合成的那条边界**上才有意义：画布配成
`alphaMode: 'premultiplied'` 时，违反它的像素合成结果未定义。

但 Glassium 的画布上**每个像素的 alpha 都是 1**：背景 pass 写 alpha 1，玻璃用预乘混合
（`one / one-minus-src-alpha`）叠上去，`a_out = a + 1·(1 − a) = 1`。实测整张画布
1225×1352 个像素 alpha 全部是 255。所以那条边界上的约束天然成立，与 alphaMode 无关。

而在 pass 内部，玻璃片元的 `rgb > a` 不是错误，是**加性光** —— 混合方程对它处理得完全正确，
高光正是这么叠上去的。在这里钳 `min(rgb, a)` 不会防住任何东西，只会在低 opacity 时把高光压平。

**什么时候要重新考虑：** 如果将来加一个「背景半透明、让页面 CSS 背景透上来」的模式，
画布上就会出现 alpha < 1 的像素，那时候配 `'premultiplied'` 就必须保证 `rgb ≤ a`。

### GPU 设备丢失：重建一次，第二次就降级

驱动重置（笔记本睡眠唤醒、驱动更新、GPU 超时）会让 WebGPU 设备丢失，这台设备上创建的
一切同时作废。

- **第一次**：在新设备上整套重建全部 GPU 资源。面板、参数、监听器原样保留，实测约 30 ms，
  恢复后的画面与丢失前逐位相同。
- **第二次**：不再重试，降级。连续丢失通常说明驱动或 GPU 本身有问题，反复重建只会让页面
  反复卡顿。`backend: 'auto'`（默认）下降到 **WebGL2**，换一块新画布继续画（一块画布只能有
  一种上下文）；WebGL2 也起不来、或者显式指定了 `backend: 'webgpu'` 时降到 `none`：新画布
  露出 CSS 兜底底色，组件换上兜底表面。

WebGL2 的上下文丢失（`webglcontextlost`）走同一套规则：第一次等浏览器恢复后重建，
第二次降到 `none`。每个后端各算各的次数。

所有情况都会在控制台高声报出来。`stage.debug.stats().deviceLosses` 给出总次数，
`stage.debug.simulateContextLoss()` 可以模拟一次（WebGPU 销毁设备，WebGL2 用
`WEBGL_lose_context`）。

（T5 到 T8 期间这里是坏的：日志写着「将尝试重新初始化」，实际上没有任何代码在重建，
画布会冻在最后一帧。）

### 裁剪：矩形与圆角跟上了，clip-path 没有

玻璃画在底下的画布上，DOM 的裁剪管不到它。所以 Glassium 自己找出每块面板的**裁剪祖先**
（`overflow` 不是 visible、或 `contain: paint` 的祖先），每帧量它们的 padding box 求交：矩形部分并进
scissor，祖先的 `border-radius` 在着色器里按裁剪区域的 SDF 抹掉圆角外的玻璃（`src/renderer/clipping.ts`、
`glass.wgsl.ts` 的 `clipCoverage`）。面板在圆角滚动容器里被滚到边上时，玻璃跟着容器的圆角裁掉。

哪些祖先算数按 CSS 的**包含块链**判断，不是简单沿 DOM 往上：absolute 的面板不会被它与包含块之间
那个不定位的 `overflow: hidden` 裁掉，fixed 的面板只被建立了固定定位包含块的祖先（transform 等）裁掉 ——
与浏览器裁 DOM 的规则一致。裁剪祖先的查找结果缓存起来，页面上的 style / class / 子节点变化之后才重找。

仍然是近似的：

- 圆角按 CSS 的规则算（padding box 的内圆角 = 外圆角减边框宽；相邻两角之和超过边长时一起缩小），但
  **椭圆角**（水平、竖直半径不同）画成圆角，取短的那个半径。
- 几层裁剪祖先求交之后，交集的某个角只有正好是某个带圆角的祖先的角时才是圆的；被另一个祖先从中间截断的角是直角
  （浏览器此时裁出来的是两个形状的交，不是圆角矩形）。
- `clip-path`、`mask` 不管。
- 滚动条盖住的那一条不管（滚动条本来就画在内容之上）。
- 合并组取成员可见区域的并集 —— 成员分在两个不同的滚动容器里时，裁得不如单块面板准。

（第一期的前 12 项里这一节写的是「裁剪不作用在玻璃上」，别把面板放进滚动容器。现在放了也行。
之后一段时间是「矩形跟上了、圆角没有」，圆角外会漏出一小块玻璃。现在圆角也跟上了。）

### 用户场景（setScene）

玻璃折射的是场景（R2），场景可以是你自己的图片、视频或画布（`stage.setScene()`）。几条边界：

- **跨源要 CORS。** 没有 CORS 授权的跨源图片与视频，浏览器不允许传进 GPU。`setScene` 里先试读一个像素，
  当场 reject 并说明原因，不会等到画的时候。按 URL 传进来的图片由 Glassium 设 `crossOrigin = "anonymous"`；
  自己建的 `<img>` / `<video>` 要自己设。
- **加载失败时浏览器不告诉页面原因**：404、格式不支持、CORS 在页面看来是同一个错误。错误信息只能按
  「是不是跨源」给提示。
- **静态图按场景分辨率缩放一次再上传。** 场景分辨率由像素预算决定，可能低于屏幕的设备像素 —— 与内置场景
  一样。视口变化时在后台重新缩放，新位图好之前继续用旧的（铺法对，清晰度差一点，不闪）。
- **传进来的 ImageBitmap 在换掉之前要保持打开**：视口变化时要从它重新缩放。提前关掉的话重新缩放失败，
  警告一次，继续用上一次缩好的。
- **视频要有第一帧才换上**：`setScene` 等 `loadeddata`。`preload="none"` 又没在播放的视频会一直等下去。
- **动图只有第一帧。** GIF、动画 WebP 按图片处理：上传前缩放成一张位图。要动画请用 `<video>`。
- **上传的代价在你那边。** 视频按新帧上传（有 `requestVideoFrameCallback` 时；没有就每帧），
  `dynamic: true` 的画布每帧上传。1080p 一帧约 8 MB，大画布请自己控制尺寸。`stats().sceneUploads`
  是累计上传次数，静态场景稳定后应当走平。
- **减少动效时动态场景停在当前帧。** `prefers-reduced-motion: reduce` 下帧循环不跑（与内置场景的时间冻结
  是同一条规则），视频和动画画布都不会更新。要推一帧用 `refreshScene()`。
- **没有 GPU 时**：URL、`<img>`、Blob 场景写成画布的 CSS 背景（同样的铺法与底色），页面照样有这张图；
  画布与视频退成兜底底色。
- 一个 stage 一个场景。逐面板不同的背景仍然不做。

### 填充（`<glass-fill>`）：只有纯色圆角矩形

填充是 CSS 摆位、Glassium 画进场景的纯色形状（`src/renderer/fills.ts`、`src/shaders/fill.wgsl.ts`）。
盒子（位置、尺寸、变换、裁剪祖先、CSS 上的不透明度）与面板共用同一段测量；颜色是注册成 `<color>` 的
`--glass-fill`（不继承、可以过渡，每帧读计算值）；圆角是 CSS 的 `border-radius`。每块画两次：一次画进场景
（玻璃折射、模糊、自适应都看得见它），一次按画布分辨率画到画布上 —— 场景目标受像素预算约束常常比画布粗，
直接看到的边缘要与 DOM 一样锐利。为此有填充的帧先把「没有填充的场景」拷一份（模糊链草稿纹理闲着的第 0 级，
不多占显存），背景上屏用那一份，否则场景分辨率的那一份放大上屏时会在边缘外渗出一圈（实测场景 0.6 倍时渗出
104 个像素，拷一份之后是 0）。

- **只有纯色**：`--glass-fill` 是一个颜色，渐变、图片不行（那要进场景就用 `setScene()`）。`oklch()`、
  `color(display-p3 …)` 这类由浏览器换算成 sRGB（在 1×1 的画布上画一个点再读回来，约 4µs，只在颜色变了时做）。
- **颜色写在 `--glass-fill` 上，不写 `background`**：stage 生效时元素自己的 CSS 背景是透明的；你给它写了
  `background`，它就是一块普通的 DOM 背景，会挡住放在它上面的玻璃（R1）。没有玻璃时 glassium.css 把
  `--glass-fill` 画成 CSS 背景。
- **永远在场景里**：填充画在所有 DOM 与所有玻璃之下，哪怕元素写在一块 `<glass-card>` 里面 —— 那样它就在那块玻璃
  底下被折射。它里面的内容（文字、图标）是普通 DOM，照常画在最上面。
- **圆角**与裁剪祖先同一个近似：椭圆角取短的那个半径；`clip-path`、`mask` 不管。
- **画的先后按注册顺序**（先注册的在下面）。组件在进文档时注册，挪动元素会重新进一次文档，所以父元素上的填充
  （一块底板）通常在它里面的填充（开关的轨道）之前 —— 一般就是文档顺序。例外是程序先建了里面的、后把外面的包上去
  却没有挪动里面的那种写法。
- **开销**：主线程每块约 8 µs（面板约 4.5 µs，多出来的是颜色与圆角那六个计算样式的读取），GPU 上每块两次
  draw（场景与画布各一次，都有裁剪矩形）；有填充的帧多一次场景大小的纹理拷贝。

### `<glass-switch>` 放在哪里

旋钮是玻璃，所以它受玻璃的全部约束：
- **别放进 `<glass-card>`**：玻璃不叠玻璃（R2）。卡片的玻璃在轨道上面，会把轨道一起模糊掉，旋钮看到的也不是卡片。
- **别放在不透明的 CSS 背景上**（R1）：背景挡住画布，轨道与旋钮都看不见。层级检查会点名那个背景。
- 要一块底板（设置列表那种），用 `<glass-fill>`：它也在场景里，画在轨道下面（见上一节的注册顺序）。

按压的缓动靠 requestAnimationFrame：标签页隐藏时停在原地，回来接着走；减少动效时直接落到终点。

### 兜底表面的圆角来自 CSS

没有玻璃时（没有 GPU、高对比度模式、stage 还没建好）组件显示 `glassium.css` 的兜底表面，
它的圆角来自 CSS 的 `border-radius`，不来自 `corner-radius` 属性 —— CSS 算不出
「短边的比例」这种圆角。改了 `corner-radius` 又想让兜底表面跟上，就同时写 `border-radius`。

### `<glass-container>` 的边界

- **一组最多合并 4 块。** 多出来的单独绘制、不参与合并，控制台警告一次。上限来自 uniform
  结构体的定长数组（4 × 128B）和片元里的循环。
- **合并组画在单块面板之后。** 两者重叠时组在上面。第一期没有全局的深度排序。
- **嵌套的容器不跨层合并。** 一块玻璃归离它最近的容器，内外两层各连各的。
- **成员的材质在颈部按 smin 的权重过渡**，所以两个 tint 不同的按钮之间会出现一段渐变。
  这是刻意的（悬停时提亮的高光会沿颈部平滑地过渡过去），但想要两边颜色泾渭分明就别放进同一个容器。
- 没有玻璃时（兜底表面）每个成员各显示各的，不会连起来 —— CSS 做不到合并。

### `<glass-button>` 在表单里：与原生按钮相同，两处例外

它是表单关联的自定义元素：在表单里默认 `type="submit"`（还有 `reset`、`button`），`name` / `value`
只在它被按下时进表单数据，`formaction` 一类的覆盖属性生效，祖先 `<fieldset disabled>` 让它禁用，
click 里 `preventDefault()` 能阻止提交。两处与原生按钮不同：

- submit 事件的 `submitter` 是一个临时的原生提交按钮（带着同样的 name / value），不是 `<glass-button>` 本身。
  规范的 `requestSubmit(submitter)` 只认原生提交按钮，传自定义元素会抛 TypeError。
- 在表单的输入框里按回车，隐式提交只认原生提交按钮 —— 不会「按下」`<glass-button>`。表单里只有一个
  输入框时浏览器照样提交（只是没有按钮的 name / value），有多个时什么都不做。需要回车提交的表单，
  放一个隐藏的原生提交按钮。

### 自适应：背后太亮或太暗时，玻璃自己蒙一层纱

默认（`adaptive: 1`，clear 预设除外）玻璃会守住与文字至少 3:1 的对比度：浅色文字下背后太亮时压暗，
深色文字下背后太暗时提亮。实测纯白背景上白字卡片的玻璃从相对亮度 1.000 压到 0.292，纯黑背景上深色字卡片从
0.027 提到 0.095（目标 0.30 / 0.10，差一点是因为按 2.2 次幂近似 sRGB 曲线）。

- 这是「可读性的下限」，不是「保证 4.5:1」。要更高的对比度，打开系统的「更高对比度」（换成磨砂）。
- 文字深浅看面板元素自己的计算颜色（`color`）。面板里不同段落颜色不一时，按面板的 `color` 算。
  页面上的 style / class 变化、窗口尺寸变化、系统切换深浅色（`prefers-color-scheme`）之后重读 ——
  靠 CSS 过渡慢慢变色的文字，要等下一次这类变化才会被重新判断。
- 背后的亮度在模糊链的粗级别上取五个点估计：很小的亮斑、很细的亮线估不进去。
- 纱是整块一样的。一块很大的面板，背后一半很亮一半很暗时，按平均值处理。
- 要关掉：`adaptive="0"`（或材质的 `adaptive: 0`），或者用 `clear` 预设。

### 投影只落在场景上

影子画在画布上，所以它和玻璃一样只落在场景上：不会落在 DOM 文字上（DOM 在画布之上），也不会落在别的玻璃上
（R2：玻璃不叠玻璃）。有投影的面板 scissor 往外扩约 29 dp，许多小面板时 GPU 的片元数跟着涨 ——
61 块 120×80 的卡片实测从 0.291 ms/帧涨到 0.328 ms/帧（高端独显）。不需要时写 `shadow="0"`。

### 减少透明度、更高对比度：玻璃换成磨砂

系统打开「减少透明度」（`prefers-reduced-transparency: reduce`）或「更高对比度」（`prefers-contrast: more`）时，
所有面板的材质多过一道变换 —— Apple 的玻璃在这两个设置下都变得更实，两者共用同一个变换
（`src/core/transparency.ts`）：模糊至少 24dp、关掉色散、表面叠一层实得多的颜色。材质自己的 tint 够显眼
（alpha ≥ 0.3）就沿用它的颜色、加厚到 0.85；否则按面板的**文字颜色**选磨砂 —— 浅色文字配深色、深色文字配浅色 ——
alpha 0.8。形状、折射、高光保留。

- 文字颜色取面板元素的计算值 `color`，页面上的 style / class 变化之后重读；只有深浅的判断翻转时才重新降级。
  面板里不同段落颜色不一时，按面板自己的 `color` 算。
- 解析不了的颜色写法（`oklch()` 之类）当作浅色文字，配深色磨砂。
- 兜底表面（没有 GPU、upgrade 之前）在这个设置下也换成深色磨砂（`glassium.css`）；兜底表面上是深色文字的话，
  在同一个媒体查询里自己覆盖。
- 更高对比度时组件另外描一圈边（`glassium.css`，`box-shadow: inset 0 0 0 1px currentColor`）：
  用文字颜色，而磨砂是按文字颜色的反色选的，所以这圈边总看得清。不用 outline，免得盖掉按钮的焦点框。
  这圈边是 CSS 媒体查询，`simulateMoreContrast()` 模拟不到它，只模拟得到 stage 的磨砂。
- `prefers-reduced-transparency` 目前只有 Chromium 支持（Safari 与 Firefox 里查询恒为不匹配，这一条不生效）；
  `prefers-contrast` 三家都支持。

### 高对比度模式下停用

`forced-colors: active` 时 stage 停用：画布隐藏、帧循环停止、组件换成 CSS 兜底表面，
由浏览器强制成系统配色。折射图像在高对比度下没有意义，还会让强制配色的文字压在一张
花哨的背景上。

### 第一期在 sRGB 编码空间混合，不在线性空间

线性空间严格更正确（σ=32 的模糊跨黑白阶跃当前会偏暗），但切过去会让每个已校准的数值全部
重定基。放在第二期，挂在开关后。

### WebGPU 不是到处都有，所以 WebGL2 兜底是强制项

Firefox 无 Linux、无 Intel Mac、无 Android；Chrome 的 Linux 受 GPU 门禁
（Intel Gen12+ 或 Wayland 上的 NVIDIA）；Chrome Android 受厂商门禁。caniuse 约 87%。
别信「WebGPU 已经 Baseline 了」这类说法 —— 细节上是错的。

T11 起这一级有了（`src/webgl2/`）：同一套光学（GLSL 由 WGSL 真源机械生成）、同一份 uniform
字节。本机实测两个后端的整帧只有 1 个像素差 1/255，见 docs/calibration.md。

WebGL2 这一级的代价：光学探针要 `EXT_color_buffer_float`（渲进 RGBA32F），没有它就只能回读
颜色、不能逐像素验光学；UBO 的偏移对齐值不整除 256 时退回逐次上传（结果一样，慢一点）。
