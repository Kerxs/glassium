# 校准记录

实测数值。写下来是为了将来改动时有个比对基准 —— 「感觉不太对」查不动，
「以前是 0.0198 现在是 0.031」查得动。

所有数字都能用 `npm test` 复现（伪随机全部定种）。

## 几何：SDF 与梯度

| 量 | 实测 | 方法 |
|---|---|---|
| `sdRoundedRect` 对独立几何分区解的最大偏差 | **< 1e-9** | 10 000 个定种伪随机点，halfSize 150×90，半径 0–90 |
| 同上，对暴力边界采样 | **< 1e-4** | 40 000 个边界样本，跳过 \|sd\| < 1.0 的点 |

暴力法的跳过阈值不是调出来的。间距 s 离散采样边界后，对距边界 d 的点，最近样本的
距离误差上界是 `sqrt(d² + (s/2)²) − d ≈ s²/(8d)`。周长约 708px、40 000 样本 →
s ≈ 0.0177 → 误差 ≈ 3.9e-5 / d。要低于 1e-4 需要 d > 0.39，取 1.0 留余量。

两条都留着是有理由的：第一条测「实现和我的推导一致」，第二条测「我的推导和实际几何一致」。
只有第一条的话，两处写错成同一个样子就能骗过去。

## 梯度场的峰值转向率

这是 `gradRadiusOf` 里那个 1.5 倍放大唯一能被量化的地方。

形状 halfSize 150×90、半径 40、取样深度 9.6px（约 0.4 × refractionHeight 24）：

| 放大倍数 | gradRadius | 峰值转向率 | 解析预期 `1/(gradRadius − 深度)` |
|---|---|---|---|
| 1.0× | 40 | **0.03289** /px | 1/30.4 = 0.032895 |
| **1.5×（采用）** | 60 | **0.01984** /px | 1/50.4 = 0.019841 |

比值 **1.66×** —— 放大之后，折射方向绕角旋转得平缓 1.66 倍。

实测与解析预期吻合到 5 位有效数字，这不是巧合：角区的方向场就是绕「放大后的角心」的
径向场，所以在离角心 `gradRadius − 深度` 处，转向率恰是它的倒数。测试直接断言这条恒等式，
而不是断言一个调出来的阈值 —— 阈值会随形状变，恒等式不会。

不同深度下的比值：

| 深度 | 1.5× | 1.0× | 比值 |
|---|---|---|---|
| 2.0px | 0.01724 | 0.02632 | 1.53× |
| 9.6px | 0.01984 | 0.03289 | 1.66× |
| 20.0px | 0.02500 | 0.05000 | 2.00× |

越深差距越大 —— 这正好落在折射最强的边缘带里。

## 折射剖面

`refractionHeight = 24px`、`refractionAmount = 48px`、`circleMap`（squircle n=2）：

| 带深 | 深度 | 位移 | 斜率 |
|---|---|---|---|
| 0% | 0.00px | 48.000px | −692.82 |
| 25% | 6.00px | 16.251px | −2.2678 |
| 50% | 12.00px | 6.431px | −1.1547 |
| 75% | 18.00px | 1.524px | −0.5164 |
| 90% | 21.60px | 0.241px | −0.2010 |
| 99% | 23.76px | 0.002px | −0.0200 |

**边界处斜率发散**（−692 只是 1e-4 步长下的有限差分值，真值是 −∞）。这是 `circleMap`
在 x=1 处的固有性质，也正是「边缘一道锐利亮边」的来源 —— 不是缺陷。但它意味着
**边界那一两个像素对采样误差极其敏感**：半个纹素的偏移在这里会被放大成可见的亮边抖动。
这是 `units.ts` 把半纹素换算收敛到一处的实际理由。

位移在 50% 带深处已经衰减到 6.4px（13%），75% 处只剩 1.5px（3%）。也就是说
**折射在观感上只占边缘带的前一半**，后一半基本是过渡。上游那个
`if (-sd >= refractionHeight) return 直通;` 的提前返回因此非常划算。

### circleMap 与 squircle(n=4) 的差别

| x | circleMap | squircle n=4 | 比值 |
|---|---|---|---|
| 0.25 | 0.03175 | 0.00098 | 0.031 |
| 0.50 | 0.13397 | 0.01601 | 0.119 |
| 0.75 | 0.33856 | 0.09072 | 0.268 |
| 0.90 | 0.56411 | 0.23421 | 0.415 |

n=4 把位移向边界进一步压缩，中心更平 —— kube.io 说的「Apple 偏好的更柔的过渡」。
差别很大（中段差 8 倍），所以这个参数值得暴露给调用方，不该写死。

## 分辨率解析

`MAX_PIXELS = 1_300_000`、`minSceneRatio = 0.5`：

```
viewport  800x600  @1x · composite  800x600  · scene  800x600 (1.000x css, 0.48MP)
viewport 1440x900  @1x · composite 1440x900  · scene 1440x900 (1.000x css, 1.30MP)
viewport 1920x1080 @2x · composite 3840x2160 · scene 1520x855 (0.792x css, 1.30MP)
viewport 2560x1440 @1x · composite 2560x1440 · scene 1520x855 (0.594x css, 1.30MP)
viewport 1512x982  @2x · composite 3024x1964 · scene 1415x919 (0.936x css, 1.30MP)
viewport 3840x2160 @2x · composite 7680x4320 · scene 1920x1080 (0.500x css, 2.07MP) · 超出预算
```

只有最后一行真的触发冲突：4K CSS 视口下预算要求 0.396×、地板要求 0.5×，无法同时满足，

**1512×982@2x 那一行是个坑，记在这里免得再踩。** 它的比例 0.936 完全由预算算出、地板没参与，

「最终像素数 > maxPixels」当判据就会在这里误报，让人去查一个不存在的冲突。
判据必须是「地板是否抬高了比例」。已有回归测试钉住。

## 本机 GPU 实测（T5）

Edge 153 / NVIDIA Lovelace（RTX 40 系）/ Windows 11。两个计划阶段悬着的问题都有答案了。

### adapter 限制

| 限制 | 实测值 | 影响 |
|---|---|---|
| `minUniformBufferOffsetAlignment` | **256** | **256B stride 的假设成立**，`PanelUniforms` 不必重排 |
| `maxUniformBufferBindingSize` | 65536 | 65536 / 256 = **单个 buffer 最多 256 个面板**，够用 |
| `maxTextureArrayLayers` | 256 | 最终没用纹理数组（见下），但留着这条数便于对比 |
| `maxTextureDimension2D` | 8192 | 8K 视口下合成目标 7680×4320 仍在范围内 |
| `maxBindGroups` | 4 | 设计用 3 组（stage / panel / 纹理），留一组余量 |

注意这是**单台机器单块显卡**的数。移动端 GPU 的 `maxUniformBufferBindingSize` 常见是
16384（= 64 个面板），真要跑移动端时得重新测。

### 动态层索引采样：可用

```
[Glassium] 能力探测：动态层索引采样=可用 · 256B stride=成立（对齐要求 256B）
```

`textureSampleLevel(layers, samp, uv, probe.layer, 0.0)` 里 `probe.layer` 来自 uniform，
编译与建管线都通过，**不需要**退回静态绑定加分支链。

不过 T6 最终没有用纹理数组，改用了 mip 链 —— 原计划那句「K 层放一个 texture_2d_array，
每层是前一层分辨率的一半」自相矛盾：**纹理数组的各层必须同尺寸**。mip 天生逐级减半，
而且浮点 level 还能让硬件自动做三线性插值，把「按 log2(σ) 手动 lerp」直接省掉。
探测到的能力（动态索引采样）是同一个，所以这条结论仍然有效，只是用在了 mip level 上。

探测代码在 `src/webgpu/probe.ts`，每次启动都跑 —— 这个答案会随驱动和浏览器版本变，
不该固化成一句注释。

### 分辨率解析（真实浏览器）

```
viewport 832x901 css @1.5x · composite 1248x1352 · scene 1096x1187 (1.317x css, 1.30MP)
viewport 1024x768 css @1.5x · composite 1536x1152 · scene 1317x987  (1.286x css, 1.30MP)
```

两例都是**预算封顶**而非地板生效：视口不大、dpr 1.5，预算允许场景渲染到 CSS 分辨率
**之上**（1.3x）但仍低于设备分辨率（1.5x），于是取预算值。`budgetExceeded` 皆为 false。

832×901 那一例的场景是 1,300,952 像素，比预算多 952 个 —— 取整溢出，不是冲突。
这正是前面记的那个坑，判据取「地板是否抬高了比例」才不会在这里误报。

## 模糊链（T6）

6 级 mip 链，σ = {0, 2, 4, 8, 16, 32}（场景像素）。每帧 **10 趟** = 2×(6−1)，
`drawCalls` 共 12（场景 1 + 模糊 10 + 呈现 1）。**趟数与面板数量无关** —— 这是共享链
的全部意义。

### σ 扫描的连续性

判据用**高频能量**（相邻像素梯度均值），不用逐帧像素差。后者在棋盘格上会剧烈振荡，
测到的是采样与摩尔纹，不是模糊本身。高频能量则必须随 σ 单调下降。

在 calibration 场景（832×901）上扫 σ = 0 → 32，22 个采样点：

| σ | 0 | 0.5 | 1 | 2 | 3 | 4 | 6 | 8 | 12 | 16 | 24 | 32 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 高频能量 | 5.188 | 5.090 | 4.795 | 4.442 | 3.949 | 3.328 | 2.046 | 1.609 | 0.766 | 0.693 | 0.593 | 0.593 |

**单调，零次回升**，且在级边界 σ = 2 / 4 / 8 / 16 处没有任何突变 ——
硬件三线性插值把相邻两级接得很平。所以 **K=6 够用，不需要提到更高**
（这是计划里列为「需要实验才能定」的一项）。

两处平台期，都在测量分辨率以下、不是缺陷：σ ∈ [1.25, 1.75] 时绝对模糊量约 1 像素，
而画布相对场景还有 1.5× 的放大；σ ≥ 24 时图像已接近平坦，高频能量触底。

### 两个测量方法上的坑

**线性渐变几乎是高斯模糊的不动点。** 在渐变场景上扫 σ，逐单位差异只有 0.007–0.044
（本底 0.003），信号小到无法判断有没有台阶。这就是把 calibration 场景从 T12 提前到 T6
的原因 —— 没有它验不了 T6 自己。同一条理由后面还会适用于折射与色散。

**WebGPU 画布在 DOM 侧读不出来。** 对它调 `drawImage` / `createImageBitmap` 得到的是
全黑，即使画面正常显示、即使 `configure` 时加了 `COPY_SRC`。必须走 GPU 侧的
`copyTextureToBuffer` + `mapAsync`（`stage.debug.readback()`）。画面明明在动而回读一片黑，
很容易被当成「渲染没出来」去查渲染，实际是读法不对。

## 玻璃 pass（T7）

### GPU 与 CPU 逐像素比对

`stage.debug.probeOptics(i)` 把第 i 块面板的光学中间量（sd、方向、位移）原样渲进
`rgba32float` 回读，`compareOptics()` 用 `src/core/optics.ts` 在同样的像素中心重算一遍比对。
探针与正常渲染共用同一段 `evalOptics`，所以验的就是实际渲染的那条路径。

三块面板、共 238,125 个纹素（DPR 1.5，calibration 场景）：

| 面板 | 纹素 | 非有限值 | max \|Δsd\| | p99 \|Δ偏移\| | max \|Δ偏移\| | 最差处 sd |
|---|---|---|---|---|---|---|
| 卡片 regular | 182,575 | **0** | 8.3e-6 | 1.7e-5 | 4.1e-4 | −0.002 |
| 胶囊 thick | 27,775 | **0** | 8.1e-6 | 6.5e-6 | 2.0e-4 | −0.002 |
| 四角不同 [4,32,8,28] | 27,775 | **0** | 3.3e-5 | 8.8e-5 | 1.4e-3 | −0.009 |

**没有一个 NaN**，包括四个角。

最大误差全部落在 **sd ≈ 0 的面板边界上**，而且正是预料之中的那种：`circleMap` 在 x=1 处
斜率发散（见上面「折射剖面」一节），f32 在 sd 上 1e-5 量级的舍入被放大成位移上 1e-3 量级
的差 —— 七百分之一个像素，看不见。离开边界（p99）就回到 1e-5 量级。

**比的是采样偏移 dir × displacement，不是 dir 本身。** 面板深处有一条 cy = cx 的对角线，
`gradSdRoundedRect` 在那里从 (1,0) 跳到 (0,1)，f32 与 f64 在紧贴它的像素上会落到不同一侧，
dir 差 90°。但那里早已在折射带之外、位移为 0，不影响渲染。以卡片为例：内部分支只在
|y| < 41 的横条里，离边缘 124 个设备像素，而折射带只有 33 个。

原计划写的判据是「1e-5 绝对误差」。sd 基本做到了；偏移在边界上做不到，也不该要求 ——
那是函数本身的性质，不是实现的误差。更有意义的判据是：**零个非有限值、p99 在 1e-4 以下、
最大误差只出现在 |sd| < 0.01 处。**

### DOM 对齐：修掉一个滚动条引起的错位

第一版按 `window.innerWidth` 分配画布像素。**innerWidth 包含垂直滚动条，而
`position:fixed; inset:0` 的画布不包含。** 1024 宽视口、15px 滚动条、DPR 1.5：

| | 修复前 | 修复后 |
|---|---|---|
| 用于换算的 CSS 宽度 | 1024（innerWidth） | 1008.67（画布自身） |
| 实际显示缩放 / 假定缩放 | 1.5228 / 1.5 | 恒等 |
| 右侧面板错位 | **7.5 CSS px（11 设备像素）** | **0** |

错位随 x 线性增长，而且**页面不滚动就没有滚动条、完全看不见** —— T5、T6 都没暴露，
直到 T7 加了几块面板把页面撑到能滚动。修法是按画布自己的 `getBoundingClientRect()` 解析视口，
于是显示缩放与换算缩放都等于 `compositeWidth / 画布 CSS 宽度`，**按构造恒等**。
另加了 `ResizeObserver`：滚动条出现或消失会让画布变宽变窄，但**不会**触发 `window.resize`。

### 滚动与缩放跟随

每帧重新量 `getBoundingClientRect()`。GPU 实际使用的面板矩形与元素当前位置的差：

| 情形 | 与元素位置的差（设备像素） |
|---|---|
| scrollY = 0 | 1.5e-5 |
| scrollY = 120 | 2.0e-5 |
| scrollY = 247（到底） | 1.4e-5 |
| 视口缩到 877×640 | 1.5e-5 |

全部是 f32 精度量级。

只在 DPR 1.5 下实测过。DPR 1 和 2 没有直接测 —— 浏览器面板改不了 DPR。但修复后的对齐
是按构造成立的（两个缩放是同一个表达式），而 1.5 这种非整数倍率本来就是取整最容易出错的情形。

## 色散与高光（T8）

### 关掉色散与高光时，与 T7 逐位相同

改着色器**之前**先对 T7 版本的整张画布（1225×1352，calibration 场景，静态）做了 SHA-256；
改完之后把三块面板的 highlight 设 0（dispersion 本来就是 0）再做一次：

```
T7    8faab693334fd376c6a18efc065144d122ea7633238506f1573b454f97c75893
T8    8faab693334fd376c6a18efc065144d122ea7633238506f1573b454f97c75893
```

六百六十万字节完全一致。场景着色器加了两种模式、uniform 从 16B 扩到 32B 之后又比了一次，仍然一致。
「dispersion = 0 走的就是 T7 那一支」于是不是一句注释，而是有哈希作证。

### 高光：只有朝光一侧发亮，背光一侧是暗边

flat 场景（处处 127/255 的灰）。模糊与折射都改变不了常数场，所以边缘上的任何亮度差都只可能
来自高光。按外法线方向分 8 个扇区，统计边缘带内像素相对 127 的亮度差（0–255）：

| 扇区 | TL | T | L | TR | BL | B | R | BR |
|---|---|---|---|---|---|---|---|---|
| 均值 | **+73.8** | +69.1 | +39.9 | +1.9 | +1.8 | −6.0 | −7.1 | **−15.6** |
| 最大 | 128 | 128 | 128 | 28 | 25 | 0 | 0 | **0** |

光源在左上 45°。左上最亮、右下暗边最深、右上与左下居中（这两个扇区里朝光与背光的像素各半）。
**BR 扇区的最大值是 0 —— 一个发亮的像素都没有。** 上游的 `abs()` 会让它和 TL 一样亮。

与 CPU 模型（`highlightTerms` × `rimMask`，再按 1px 覆盖率混合）逐像素比对 173,145 个像素，
最大差 **1.1/255**，就是 8 位量化。

T 比 L 亮是亚像素采样造成的，不是光照不对称：卡片上边落在 y = 604.98、左边落在 x = 42.5，
两条边上像素中心到边界的距离不同，采到的 rimMask 不同。CPU 模型把这个也复现了。

### 色散：四个角上蓝都比红采得更靠里

radial 场景，圆心放在卡片中心，亮度随距离单调增加 —— 往里采就是往暗处采。
色散让蓝通道采得比红通道更靠里，于是边缘上应当**蓝比红暗**。dispersion = 0.5，
统计折射带内（位移 > 2px）像素的 R − B（0–255）：

| 扇区 | TL | TR | BR | BL | T | R | B | L |
|---|---|---|---|---|---|---|---|---|
| 均值 | **+5.70** | **+5.70** | **+5.70** | **+5.70** | +5.58 | +5.77 | +5.17 | +5.84 |
| 最小 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| R > B 的比例 | 0.985 | 0.982 | 0.979 | 0.981 | 0.979 | 0.991 | 0.981 | 0.994 |

四个角**完全一致**（5.70），每个扇区的最小值都是 0 —— 从没有反过来的。剩下约 2% 的像素是
R 与 B 量化到了同一个 8 位值，不是反向。

对照：同一块面板、同一个场景，dispersion = 0 时 **max |R − B| = 0**。上面测到的差全部来自色散。

上游的鞍面调制在这组测量里会给出 TL/BR 与 TR/BL 相反的符号。`src/core/lighting.test.ts`
在 CPU 上把上游的写法也实现了一遍作对照，证明这组判据分辨得出两者。

### 两个测量上的坑

**画布是 bgra8unorm。** Windows 上 `getPreferredCanvasFormat()` 返回的是 BGRA，回读的原始字节
第 0 个是蓝不是红。直接拿原始字节比 R 和 B，色散的结论会整个反过来，而且反了也看不出来 ——
「蓝比红暗」和「红比蓝暗」都像是一个合理的结果。`readback()` 现在一律换成 RGBA 再返回。

**Math.min(...array) 会撑爆调用栈。** 一整块面板十八万个像素，展开到参数列表上会直接抛
RangeError。汇总函数改成了循环。

## 设备丢失与恢复

`stage.ts` 拆成两层之后：外壳（画布、面板注册表、调试参数、帧循环、监听器）跨设备存活，
一台设备上的全部资源在 `gpu.ts` 的 `GpuRenderer` 里，可以整体丢弃、整体重建。

用 `simulateDeviceLoss()` 模拟（销毁当前设备但不记为主动释放；真实驱动重置的 reason 是
`unknown`，模拟的是 `destroyed`，stage 不看 reason，走同一条路径）。整帧 SHA-256 作为判据：

| 步骤 | 结果 |
|---|---|
| 拆分重构之前 | `03664e19…e647`（calibration，色散 0.3，高光 0.7） |
| 拆分重构之后 | 同上 —— 重构没有改变任何输出 |

### 它抓到的一个问题：校准场景的硬边压在像素中心上

第一次跑，跨后端那一项失败：对角线上 500 个像素差 250/255。差异的包围盒是
(0, 191)–(818, 1009)，正好是 x + y = 1009 这条线。

原因在测试场景，不在渲染器。校准场景的对角线是 `step(0, p.x + p.y − (W + H)/2)`，
像素中心 p = (x + 0.5, y + 0.5)，所以 **W + H 为偶数时整条对角线的像素中心恰好落在边上**，
step 比较的两边在数学上相等，结果取决于 uv 插值的最后一位 —— 两个后端各判各的。
playground 的画布宽 805（有滚动条），W + H 为奇数，碰不到；verify.html 没有滚动条，
画布宽 820，碰上了。竖直阶跃 `step(W/2, p.x)` 在 W 为奇数时有同样的问题。

修法：两条硬边各挪 1/4 像素，永远不经过像素中心。这对「本来就不经过像素中心」的尺寸
结果完全不变，只让原来那一排取值不定的像素定下来。实测（805×1200 @1x，改动前后按列
做校验和）：**只有 x = 402 这一列、第 600–1199 行变了** —— 正是 W = 805 时竖直阶跃压着
像素中心、又在对角线以下可见的那一段；其余 804 列逐位不变。

所以本文档 T12 之前记下的整帧哈希（`03664e19…`、`d494d93c…`、`a67d1768…` 等）只在

## 与上游 playground 的对照（T12）

### 为什么是数学层面的对照，而不是截图

上游没有 Web 演示：它的 catalog 只以 Android APK 的形式提供（README 里没有 JS / Wasm 构建或
GitHub Pages）。在本机跑上游要装 JDK、Gradle、Android SDK 与模拟器，这台机器上都没有，装一整套
工具链超出了这次的范围。所以对照做在**源码与数学**上：读上游在锁定 commit
（`65ab177e`）上的 `GlassPlaygroundContent.kt`、`Lens.kt`、`Blur.kt`、`ColorFilter.kt`、
`Highlight*.kt` 与 `Shaders.kt`，把它的折射着色器原样转写成 TS，与 Glassium 逐像素比
（`src/core/upstream.test.ts`）。

像素级的并列截图仍然是待补项（见下）。

### 上游 playground 的真实配置

规划阶段那张表有两处记错了，这里按源码更正：

| 控件 | 默认 | 范围 | 进入效果链的方式 |
|---|---|---|---|
| Corner radius | 0.5 | **0–1**（计划写的 0–0.5） | `RoundedRectangle(256.dp / 2 · frac)`，玻璃是 256dp 的正方形 |
| Blur radius | 0 | 0–32 dp | `blur(radius.dp.toPx())` —— **半径**，不是 σ |
| Refraction height | 0.2 | 0–1 | `refractionHeight = frac · minDim · 0.5` |
| Refraction amount | 0.2 | **0–1**（计划写的 −1–1） | `refractionAmount = frac · minDim` |
| Chromatic aberration | 0 | 0–1 | `chromaticAberration = value > 0f` —— **一个开关**，滑杆只决定开或关 |

此外固定叠着 `vibrancy()`（饱和度 1.5）、`depthEffect = true`、`Highlight.Plain`，没有表面 tint。
效果顺序是 vibrancy → blur → lens，与 Glassium 的规范顺序一致。

### 逐项对照

| 项 | 结果 |
|---|---|
| 主玻璃的折射（默认配置：256×256、圆角 64、height 25.6、amount 51.2、depthEffect 开） | **逐像素相同**：65 536 个像素里 25 068 个在折射带内，采样偏移最大差 **0**（f64 下逐位） |
| 控件面板的折射（`lens(16dp, 32dp)`、32dp 圆角、depthEffect 关） | **逐像素相同**：20 948 个折射像素，最大差 0 |
| 四角半径不同（256×128，[4, 32, 8, 28]） | 最大差 **28.3 px** —— 上游 radiusAt 的坐标系 bug，四角塌缩成右下角 |
| 材质降级 | `lowerMaterial({ refraction: 0.2, distortion: 0.2, cornerRadius: '0.5frac' })` 在 256×256 上得到的 height / amount / 四角半径与上游完全相同 —— 两条缩放规则就是照抄的 |
| 饱和度 | 形式相同（`s·c + (1 − s)·luma`）。上游的亮度权重是 0.213 / 0.715 / 0.072，Glassium 用 Rec.709 的 0.2126 / 0.7152 / 0.0722；s = 1.5 时整个 RGB 立方体上最大通道差 **< 0.1/255** |
| 模糊 | **量纲不同。** 上游的 `blur(r)` 是半径：Android 上 `RenderEffect.createBlurEffect` 经 hwui 的 `Blur::convertRadiusToSigma` 换成 **σ = 0.57735·r + 0.5**（像素）后交给 Skia（已从 AOSP 源码确认）。Glassium 的 `blur` 直接就是 σ（dp）。所以上游 `blur(4dp)` 在 density 1 下相当于 Glassium 的 `blur: 2.8` 左右。Compose 在非 Android 平台（skiko）上把 BlurEffect 交给平台实现，那边的换算没有核实 |
| 色散 | **刻意不同。** 上游是开关（固定强度）、七次采样的离散谱、鞍面调制（相邻两角彩边方向相反）；Glassium 是连续的 `dispersion`、三通道、径向（四角一致）。见 porting-notes 第 2 条 |
| 高光 | **刻意不同。** playground 用的 `Highlight.Plain` 是一圈 0.5dp 宽、0.25dp 模糊、0.38 白、Plus 混合的**无方向**描边；上游默认的 `Highlight.Default` 是 `abs()` 的对称高光。Glassium 是左上受光、右下暗边的不对称高光。三者之间没有数值对应 |
| 表面 tint | 上游 playground 的主玻璃没有；Glassium 的 regular 预设默认有 0.18 的白色叠加。要对齐就写 `tint: 'rgba(0,0,0,0)'` |

用 Glassium 的材质写出上游 playground 的默认玻璃，是：

```ts
{ cornerRadius: '0.5frac', refraction: 0.2, distortion: 0.2, depthEffect: 1,
  blur: 0, saturation: 1.5, tint: 'rgba(0, 0, 0, 0)', dispersion: 0 }
```

折射部分与上游逐像素相同；高光与色散是刻意的重写，不追求一致。

## 多面板的帧开销

playground 上另加 0 / 8 / 16 / 32 / 64 块 120×80 的 `<glass-card>`（带色散），
画布 1207×1800 @1.5（场景 934×1392），Edge / RTX 40 系。面板隐藏时 rAF 不跑，
所以每一帧都是 `renderNow()` 同步出的，没有别的帧混进来。

- **主线程**：连续 300 帧取平均（`performance.now()` 在没有跨源隔离的页面上只有 0.1ms 的分辨率，
  单帧量不出来）。`stats().cpuMs` 分出「测量」（量所有面板）与「整帧」（测量 + 打包 + 编码提交）。
- **GPU**：连续提交 100 帧、最后只等一次 `onSubmittedWorkDone`，按吞吐算每帧。主线程每帧比这个快，
  所以这个数由 GPU 决定。

| 面板（含合并组成员） | drawCalls | 主线程每帧 | 其中测量 | 每帧（GPU 吞吐） |
|---|---|---|---|---|
| 5 | 16 | 0.067 ms | 0.017 ms | 0.25 ms |
| 13 | 24 | 0.081 ms | 0.035 ms | 0.23 ms |
| 21 | 32 | 0.096 ms | 0.052 ms | 0.30 ms |
| 37 | 48 | 0.131 ms | 0.077 ms | 0.29 ms |
| 69 | 80 | 0.179 ms | 0.120 ms | 0.27 ms |

每多一块面板，主线程约多 **1.7 µs**，几乎全在测量那一段（`getBoundingClientRect` + `checkVisibility`）。
69 块面板时整帧主线程 0.18 ms，是 60fps 帧预算的 1%。GPU 这一侧被场景、10 趟模糊与上屏这些
固定开销主导，面板从 5 块加到 69 块看不出变化。

计划里写过「超过 32 块面板警告一次」—— 按这组数没有理由警告，所以没有加。

两条保留：这是一块高端独显上的数，移动端与核显要重新测；测量时 DOM 在帧与帧之间没有变化，
`getBoundingClientRect` 不会触发重新布局。页面每帧都改 DOM 时，第一次读几何会强制布局 ——
那是页面自己的布局开销，不是 Glassium 的，但会算在「测量」这一段里。

## 用户场景（第一期之后）

playground 上实测（`?scene=user:photo` 等），画布 1207×1800 @1.5（场景 934×1392），Edge / RTX 40 系：

| 场景 | 实测 |
|---|---|
| 3000×2000 的 JPEG（Blob） | 解码后缩到 2088×1392（cover：纵向正好是场景高，横向多出来的裁掉）再上传，**1 次**；之后 1550 帧不再上传 |
| 同一张图，视口从 820×1200 改到 700×1000 | 后台重新缩放，上传 **+1**；bind group +16（模糊链按新尺寸重建，加上新尺寸的场景纹理） |
| 960×540 的动画画布，`dynamic: true` | 10 帧上传 10 次 |
| 同一块画布录成 30fps 的流、放进 `<video>`（不在 DOM 里） | 2 秒 481 帧（面板 240Hz）上传 **60** 次 —— 正好是视频的帧率。`requestVideoFrameCallback` 对不在 DOM 里的视频照样触发 |
| WebGL2 上同样的图片与视频 | 图片 1 次；视频 480 帧上传 60 次 |
| `createGlassStage({ scene, sceneOptions: { background: '#ff00ff' } })` | 图片解码完成之前的那一帧是底色（255, 0, 255），之后是图片；共上传 2 次（占位的透明像素 + 图片） |
| 加载失败、被后一次调用取代 | 同源 404 提示「检查地址与格式」、跨源提示 CORS；被取代的调用一律 reject `AbortError`（即使它自己也加载失败了） |
| 没有 GPU（`?glassium.simulate=no-webgpu&glassium.backend=webgpu`） | 画布的 CSS 背景变成 `url("blob:…") center / cover no-repeat`，照片照样铺满页面，组件显示兜底表面 |
